To regain and exceed your previous performance (targeting 10k+ PUTs and 20k+ GETs), you need to strip the design down to its bare metal essentials. The current implementation is "over-engineered" with safety and abstraction layers that kill throughput.
Here is the strategic roadmap to fix p2:
1. What to REMOVE Immediately (The "Extra" Work)
These components are actively destroying your performance. Remove or bypass them:
❌ Remove asyncio.to_thread for I/O:
Why: You are paying the cost of thread pool scheduling (context switch + queue latency) for every single operation.
Fix: Use Non-Blocking I/O (os.open with O_DIRECT or O_NONBLOCK) or rely on the OS page cache with standard async file handles. If you must block, do it in a dedicated writer thread that processes a queue, not one thread per request.
❌ Remove Per-Request fdatasync:
Why: Calling fdatasync forces the disk head to seek and flush immediately. This caps throughput at ~100-200 ops/sec on spinning rust and limits SSDs significantly.
Fix: Rely on the OS writeback cache. Only fsync when rotating volumes or on graceful shutdown. If durability is critical, use a Write-Ahead Log (WAL) that is fsynced in large batches, not per object.
❌ Remove JSON Metadata Parsing in Hot Path:
Why: Parsing JSON strings for block coordinates on every GET is CPU-intensive.
Fix: Store metadata in LMDB as binary structs (e.g., Python struct.pack or raw bytes) representing [volume_id, offset, length]. No JSON serialization/deserialization.
❌ Remove "Batch Window" Logic for Single Writes:
Why: Waiting for a timer or batch size adds latency.
Fix: Implement a Ring Buffer or Memory Mapped File (mmap) approach. Writers just copy bytes into a shared memory segment; a single background thread flushes that segment to disk sequentially.
2. The High-Performance Architecture (The "New" Strategy)
To double your performance, switch to this model:
A. The "Zero-Copy" Write Path (PUT)
Instead of Receive -> Buffer -> Hash -> Thread -> Lock -> Write -> Sync, do this:
Pre-Allocation: Pre-allocate volume files (e.g., 1GB chunks) using fallocate. This removes filesystem fragmentation overhead.
Atomic Offset Counter: Use a simple atomic integer (or a locked integer in a dedicated writer thread) to claim space.
Thread A claims: Offset 1000, Length 500.
Thread B claims: Offset 1500, Length 200.
No locks needed during the actual write if offsets don't overlap.
Direct Memory Copy:
If using Python: mmap the volume file. Copy incoming bytes directly into the mmap region.
This bypasses the kernel syscall overhead of write().
Async Metadata Commit:
Push the (key, volume_id, offset, length) tuple into a lock-free queue.
A dedicated "Metadata Flusher" thread pops batches of 100-1000 items and writes them to LMDB in a single transaction.
Result: 1000 objects = 1 DB transaction instead of 1000.
B. The "Fast-Path" Read Path (GET)
Instead of Lookup JSON -> Open FD -> Seek -> Read -> Close, do this:
Binary Lookup: Query LMDB for binary struct. Unpack instantly.
Persistent Mmap: Keep volume files memory-mapped permanently.
Do not open/close files.
Access data via mmap_obj[offset : offset+length].
This is essentially a RAM read if the OS cache is warm.
Zero-Copy Response: Stream the mmap slice directly to the RSGI response body without copying to a temporary buffer.
